1. Arquitectura y tecnologías

El sistema tiene dos piezas que se comunican por HTTP con JSON:

  • Backend: API REST en Java 21 con Spring Boot 4.1 (Spring Web, Spring Data JPA con Hibernate 7, Bean Validation, Actuator, springdoc OpenAPI). Contraseñas con BCrypt (spring-security-crypto). Organizada en capas: controller → service → repository → model, con DTO de entrada y salida.
  • Frontend: páginas estáticas en HTML, CSS y JavaScript sin librerías. La página pública consulta el catálogo; las pantallas internas (panel, caja y cuentas) usan la sesión.

3. Requisitos para trabajar en el proyecto

  • JDK 21 y Maven 3.9 o superior.
  • Para el modo local: MySQL 8 (por ejemplo, con XAMPP).
  • Un servidor de archivos estáticos para el frontend: jwebserver (viene con el JDK), la extensión Live Server de VS Code o python -m http.server.
  • Opcional: Postman y Docker.

4. Correr el sistema en un computador

Modo demo (sin instalar base de datos)

Usa H2 en memoria y carga los datos de ejemplo. Todo se pierde al apagarlo.

cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=demo

Modo local (MySQL)

  1. Encender MySQL y ejecutar, en orden, los scripts de database/scripts: 01-crear-base-de-datos, 02-crear-tablas-base-de-datos y 03-crear-relaciones-fk.
  2. Arrancar el backend sin perfil (por defecto es local): mvn spring-boot:run. Hibernate valida que las entidades coincidan con las tablas.

Frontend

jwebserver -d frontend -p 5500

Abrir http://localhost:5500. La dirección de la API está en frontend/js/config.js: en el computador usa http://localhost:8080 y publicada usa https://papeleria-matrix-api.onrender.com.

6. Seguridad: sesión, roles y contraseñas

  • Inicio de sesión: POST /api/sesion con nombreUsuario y contrasenia. Devuelve un código aleatorio de 32 bytes que el navegador manda en Authorization: Bearer …. Las sesiones se guardan en memoria (AlmacenDeSesiones): al reiniciar el servidor hay que volver a entrar.
  • Cierre por inactividad (RNF-18): la sesión se cierra tras 15 minutos sin uso; cada petición renueva el tiempo. El frontend también cuenta ese tiempo y lleva al inicio de sesión con un aviso.
  • Bloqueo: después de 5 contraseñas incorrectas seguidas, el usuario queda bloqueado 5 minutos (respuesta 429). El mensaje de error no revela si el usuario existe, y la comparación tarda lo mismo exista o no.
  • Contraseñas: se guardan con BCrypt y ninguna respuesta las incluye (@JsonIgnore). Al cambiar la contraseña (de un usuario, un administrador o un operador) o borrar un usuario se cierran sus sesiones en todos los navegadores.
  • Clave de la API: la cabecera X-API-Key da acceso de administrador para Postman, Swagger y las pruebas. La comparación es de tiempo constante.

Ejemplo: registrar una venta

POST /api/ventas
Authorization: Bearer <código de la sesión>
{
  "articulos": [
    { "tipo": "producto", "id": 2, "cantidad": 1 },
    { "tipo": "servicio", "id": 1, "cantidad": 3 }

Responde 201 con la venta: código de factura de 15 cifras, total, operador y artículos. Si no alcanzan las existencias responde 409 con cuántas quedan y no se vende nada.

8. Ventas, facturas y existencias

En la base no hay tabla de ventas: una venta es una factura_del_negocio con un detalle_de_factura por artículo (Servicio_id, Producto_de_papeleria_id o Ropa_id con su cantidad). VentaService:

  • Junta los artículos repetidos en una línea y calcula el total con los precios del catálogo.
  • Descuenta las existencias de la papelería en la misma transacción; si una no alcanza, no se guarda nada (409).
  • Guarda la factura con tipo «Venta en tienda» y un código de 15 cifras (fecha y hora más 3 al azar, sin repetir).
  • Al anular, devuelve las existencias y borra la factura con sus detalles.

Varias personas a la vez

  • Existencias: la venta, la anulación y el cambio de un producto bloquean la fila del producto (SELECT … FOR UPDATE) hasta terminar. Si dos ventas piden la última unidad a la vez, una pasa y la otra recibe 409. Las filas se bloquean siempre en el mismo orden para que dos ventas no se esperen en cruz.
  • Formulario con datos viejos: el panel manda cantidadAnterior al cambiar un producto; si no coincide con las existencias de ese momento (se vendió algo mientras se editaba), responde 409 «Las unidades cambiaron» y no se guarda.
  • Precio cambiado durante la venta: la caja manda totalEsperado; si no coincide con el total calculado con los precios actuales, responde 409 «Los precios cambiaron» y no se guarda.
  • Anular dos veces: la factura también se bloquea; la segunda anulación responde 404 y las existencias se devuelven una sola vez.
  • Ropa: cada prenda es única: se vende de a una, una prenda que ya aparece en una venta responde 409 y la API de ropa devuelve disponible: false. Al anular la venta vuelve a estar disponible.

Los servicios no llevan existencias en la base de datos. La base guarda el total de la factura pero no el precio de cada línea: al consultar una venta, cada artículo muestra el precio actual del catálogo.

9. Ingresos, estadísticas y reportes

  • Ingresos (IngresoDelNegocioService): suma lo vendido por tipo en un periodo. Las facturas con tipo «servicio», «ropa» o «papelería» suman su monto; las ventas de la caja («Venta en tienda») mezclan tipos, así que se suman por línea (cantidad por precio del catálogo).
  • Estadísticas (EstadisticaDelNegocioService): número de facturas, unidades vendidas por tipo y valor promedio por venta.
  • Historiales: cada cálculo guardado con /calcular deja un historial con el rango de fechas escrito en palabras.
  • Pantalla de Cuentas: muestra las cifras del periodo calculadas con las ventas, el catálogo y los operadores, y «Guardar este corte» llama a /api/ingresos/calcular y /api/estadisticas/calcular.

10. Base de datos

Son 15 tablas: usuario, administrador, operador_de_cibercafe (herencia por tabla unida), clave_de_permiso, servicio, producto_de_papeleria, ropa, factura_del_negocio, detalle_de_factura, informacion_del_negocio, ingreso_del_negocio, historial_ingreso_del_negocio, estadistica_del_negocio, historial_estadistica_del_negocio y reporte_del_negocio. Los scripts están en database/scripts y los diagramas entidad-relación y relacional en 02-diagramas.

En el modo demo Hibernate crea las tablas desde las entidades y carga demo/datos-demo.sql (catálogo, usuarios y ventas de ejemplo) y demo/datos-demo-negocio.sql (módulos del negocio).

12. Pruebas

cd backend
mvn test

Son 85 pruebas automáticas: controladores con MockMvc y el filtro de acceso incluido (catálogo, productos, servicios, sesión, ventas, usuarios, rutas, CORS), servicios de ingresos y estadísticas con Mockito, validaciones de los modelos, el almacén de sesiones con un reloj simulado, el rol en la base (RolEnLaBaseTest) y casos con varias personas a la vez contra el servidor real (ConsistenciaTest: ventas simultáneas, doble anulación, prenda única, formulario viejo y precio cambiado). En Windows, ConsistenciaTest necesita poder abrir conexiones locales. La colección de Postman (postman/) tiene carpetas de estado, servicios, seguridad, catálogos, sesión y permisos, y ventas. El detalle está en 05-pruebas/Informe-de-pruebas-Papeleria-Matrix.pdf.

13. Integración continua y despliegue en Render

  • GitHub Actions (.github/workflows/ci.yml): en cada pull request a main y en cada cambio de main compila y prueba el backend, y construye la imagen Docker.
  • Render (render.yaml, Blueprint):
    • papeleria-matrix-api: servicio Docker, plan gratuito, perfil demo, chequeo de salud en /actuator/health, clave de la API generada por Render y CORS para la página.
    • papeleria-matrix-web: sitio estático con la carpeta frontend, con cabeceras X-Frame-Options y X-Content-Type-Options.
  • Ambos se publican solos cuando un cambio llega a main y pasan las revisiones de GitHub Actions.
  • Direcciones: https://papeleria-matrix-web.onrender.com y https://papeleria-matrix-api.onrender.com.

14. Mantenimiento y problemas conocidos

  • Datos en Render: la API publicada corre en modo demo con H2 en memoria; los datos vuelven a los de ejemplo cada vez que el servicio se reinicia o se duerme. Para guardar datos de forma permanente hay que conectar una base MySQL con el perfil local y las variables DB_*.
  • Usuarios de prueba: sus contraseñas están en el repositorio, así que cualquiera puede entrar a la versión demo. En una instalación real no se cargan.
  • Plan gratuito: el servicio se duerme tras un rato sin uso y la primera petición tarda cerca de un minuto.
  • Sesiones en memoria: funcionan con una sola instancia del servidor; para varias habría que guardarlas en una base compartida.
  • Precio por línea: la base no guarda el precio de cada línea de la factura; los totales por tipo usan el precio actual del catálogo.
  • CORS: el método PATCH no está entre los permitidos para el navegador; la página usa PUT para cambiar la clave de permiso.
  • Rol en H2: el rol del usuario se guarda como texto. Si fuera un enum, Hibernate crearía en H2 una restricción CHECK con la «é» que falla en cada conexión nueva del grupo (a los 30 minutos) y el operador ya no podría entrar. La prueba RolEnLaBaseTest lo vigila.
  • Hora: la imagen Docker usa la zona horaria de Colombia (TZ=America/Bogota); sin eso, las ventas de la noche quedarían con la fecha del día siguiente.
